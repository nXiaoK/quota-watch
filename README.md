# Quota Watch

独立运行的 OpenAI / Codex OAuth 账号 7d 额度监控服务，通过 Sub2API 管理员 API 读取主站已保存的快照，发送 Telegram / SMTP 通知，并按开关重置指定用户订阅。也可在站点空闲时通过管理员 API 自动更新 Sub2API。

## 功能

- 中文 Web 管理页，账号与订阅跨页勾选、名称/分组筛选、规则模拟及执行历史。
- 独立登录页，支持退出登录；浅色/深色主题可切换并记住当前浏览器的选择，首次访问跟随系统主题。
- 默认每 60 秒读取一次主站记录；检测已保存的原始 7d 百分比 `>0 → 0`，默认 5 秒后再次读取主站记录复核。
- 普通 Codex 与 Spark 分别读取自己的存量 7d 快照；缺失字段、无周窗口、请求失败都视作未知，不补刷。
- 每条规则绑定一个或多个来源账号和固定订阅；任一来源账号重置即可触发该规则。
- Telegram 与邮件分别启用，支持渠道测试、失败退避和恢复提醒。
- 全局自动重置和规则自动重置均默认关闭；日/周/月周期独立选择，建议仅选周用量。
- 可选的 Sub2API 原地自动更新：站点连续 10 分钟没有使用记录时更新，或在指定时段内等待空闲后更新；两种触发方式可独立开启。
- 全局自动重置关闭时，Telegram 归零通知可提供“重置选定订阅”和“忽略”按钮，由收件人手动选择。
- 事件、采样基线、动作及通知结果保存在 SQLite；配置使用 AES-GCM 加密；单数据目录只允许一个进程。

首版采用严格归零检测。持续使用的账号可能在重置后第一次采样时已恢复到非零，因此会漏掉未观察到零的周期；当前没有“全部账号重置”或“周期切换推断”模式。

要先在本机模拟 `40% → 0%` 并验证真实 Telegram/邮件通知，参阅 [本地通知测试步骤](TESTING.md)。提供的模拟主站不连接上游，也不修改真实主站订阅。

若要在完整 Sub2API 原后台查看账号和订阅变化，参阅 [真实本地测试站](REAL_SITE_TESTING.md)。该方式使用独立 PostgreSQL/Redis 和真正的管理员 API。

## 数据来源与上游请求约束

**本服务检测、复核、账号列表、连接检查及模拟均不触发上游账号请求。**

- 额度监控仅调用主站的账号列表/详情、订阅列表，以及开关启用后的订阅批量重置接口。启用 Sub2API 自动更新后，还会读取全站使用记录并调用系统更新接口。
- 通过 `GET /api/v1/admin/accounts/:id` 读取账号记录中已有的 `extra.codex_7d_used_percent`、窗口时长、重置时间及 `codex_usage_updated_at`，没有直接连接主站数据库。
- 不调用 OpenAI quota、账号 usage、token 刷新、账号测试或上游重置券入口；快照缺失时没有主动查询回退。
- 主站数据库内的原始百分比保持原值；超过 `reset_at` 不会自行归零。重复读到同一快照会显示等待更新。
- 非零基线之后必须出现更新时间更晚的真实存储快照，才允许判断归零。复核再次读取同一份已保存快照也可确认记录仍为零，复核不代表独立的上游采样。
- 主站无新快照时，本服务不能及时获知上游重置。普通 Codex 快照通常由已有业务响应头写入；Spark 影子快照目前依赖主站自身已有的专用采集结果，常规请求不会更新它，本服务不会为此补查。
- 主站 `codex_usage_updated_at` 是多个窗口共用时间，无法严格证明每次变更都独立重新采样了 7d。这里识别的是主站存量快照的归零变化，实际发生时间与发现时间可能不同。

Telegram/SMTP 通知会访问你配置的通知渠道。主站自身原有业务请求和后台任务由主站配置控制，本服务不会通过读取快照唤醒上游额度查询或重置券逻辑。

## Docker Compose

首次部署，从独立仓库克隆并在仓库根目录执行：

```sh
git clone https://github.com/nXiaoK/quota-watch.git
cd quota-watch
cp .env.example .env
# 编辑 .env，设置 QUOTA_WATCH_PASSWORD；可用 openssl rand -base64 24 生成登录密码。
docker compose up -d --build quota-watch
```

**已有 Docker 部署请先参阅 [生产环境更新步骤](UPDATING.md)**，保留原数据卷、`.env`、密钥及网络配置后再启动。直接换目录运行 Compose 可能使用新的空数据卷；不要用 `.env.example` 覆盖已有 `.env`。

打开 `http://127.0.0.1:8091`，在登录页使用 `.env` 中的用户名和密码登录。登录页及工作台都可以切换浅色/深色主题。默认仅映射本机端口；远程访问可使用 SSH 隧道：

```sh
ssh -L 8091:127.0.0.1:8091 user@server
```

也可通过 HTTPS 反向代理访问。登录应通过 HTTPS 或本机/SSH 隧道传输。反向代理需要保留 Host，不要开放跨站 API。

登录使用服务端会话和 HttpOnly、SameSite=Strict Cookie，绝对有效期为 12 小时；退出登录会立即使该会话失效，重启服务后需重新登录。用户名和密码仍由 `QUOTA_WATCH_USERNAME` / `QUOTA_WATCH_PASSWORD` 配置，不再使用浏览器 Basic 认证弹框。浏览器只保存主题偏好，不在 localStorage 中保存凭据或会话令牌。

连接设置中的主站 URL 填 Sub2API 可访问地址，管理员 Key 使用主站已有管理员 API Key。容器内的 `127.0.0.1` 指当前容器；同一 Docker 网络可用主站服务名，例如 `http://sub2api:8080`，并将服务加入该网络。

主站管理员 Key 是管理权限凭据。新服务不会自动重新生成主站 Key。主站原有认证、合规确认及面板限流仍适用；连接测试会展示失败原因。

## 配置步骤

1. 进入“连接设置”，填写主站地址与管理员 Key，测试连接后保存。
2. 配置 Telegram Bot Token、Chat ID（可配置 HTTP/HTTPS/SOCKS5 代理），或 SMTP 主机、端口、用户名、密码、发件人和收件人，发送测试通知。
3. 勾选来源账号，在“联动规则”新建规则，勾选目标订阅及重置周期。一个用户可能有多个分组订阅，应核对订阅 ID。
4. 先保持自动重置关闭，模拟规则并查看有效/跳过的订阅，保存规则后检测以建立基线。
5. 需要自动执行时，同时开启规则的自动重置和全局自动重置。关闭全局开关可暂停后续动作；已提交给主站的请求可能已经执行。

## Sub2API 自动更新

在“连接设置”中配置 Sub2API 自动更新。空闲更新和定时更新两个开关默认都关闭，可以分别启用：

- **空闲更新**：检测到可用更新后，最近 10 分钟内没有任何全站使用记录时尝试更新。执行前再次读取使用记录，确认仍满足空闲条件。
- **定时更新**：默认使用 `Asia/Shanghai` 时区的每日 `02:00–03:00` 时间窗，可修改开始时间、结束时间和时区；结束时间须晚于开始时间，且在同一天。进入时间窗后等待站点空闲；直到窗口结束仍不空闲，就跳过当天，不在忙碌时强制更新。

任务每分钟判断一次触发条件。版本检查通常每 6 小时进行一次；进入定时时间窗时可能额外检查，避免错过当天窗口。读取使用记录失败时跳过本次尝试，不会视作空闲。两个开关同时开启时，任一条件满足即可触发更新。设置页显示最近的更新状态。

更新沿用 Sub2API 后台的管理员 API：先请求 `GET /api/v1/admin/system/check-updates?force=true`，有可用更新时请求 `POST /api/v1/admin/system/update`。只有更新成功且响应要求重启时，才请求 `POST /api/v1/admin/system/restart`，随后确认服务恢复及运行版本。自动更新只适用于 Sub2API 标记为 `release` 的构建。`timezone` 是本服务用于计算时间窗的配置，不是 Sub2API 更新检查接口的参数。更新期间 Sub2API 会短暂不可用；其 Compose 服务需设置 `restart: unless-stopped` 或 `restart: always`，使进程正常退出后也能重新启动。

需要获知更新结果时，可分别开启“更新成功后通知 Telegram”和“更新成功后通知邮件”；两个通知开关默认关闭，并沿用下方各通道已启用的 Bot/Chat ID 或 SMTP 配置。只有完成更新、重启并确认运行版本已升级后，才会将成功通知加入持久化队列；更新失败、结果未知或已经是最新版本都不会发送成功通知。通知发送失败会按现有退避机制重试，发送结果可在“事件历史 → 通知记录”查看，不影响已确认的更新成功状态。

若更新请求中断或 Quota Watch 在更新期间重启，结果无法确认时会停止后续自动尝试。请先在 Sub2API 核对运行版本；必要时从其后台手动重启。确认状态后，可在 Quota Watch 设置页点击“已核对，允许再次自动尝试”解除阻塞。明确失败的任务当天不会自动重复提交。

**Docker Compose 部署注意**：这一方式替换的是当前容器内的 Sub2API 可执行文件，不会更新 Docker 镜像。以后执行 `docker compose up --force-recreate`、重新部署或重建容器时，仍可能从旧镜像恢复到旧版本；请另行维护 Compose 所用镜像版本。

空闲判断依据使用记录的写入时间。如果站点从未产生使用记录，会从首次观察到空列表起再等待 10 分钟。仍在进行中的长请求可能尚未产生使用记录，因此“10 分钟无记录”不能证明在途请求为零，也不能保证更新时完全不会中断请求。

## 详细运行日志

在“连接设置 → 快照检查与自动执行”开启“详细运行日志”，点击“保存全部设置”。默认关闭；保存后对下一条请求即时生效，不需要重启容器，服务重启也会保留选择。

日志写入进程的标准日志输出，在本目录执行：

```sh
docker compose logs -f --tail=100 quota-watch
```

使用其他容器名称时，也可执行 `docker logs -f --tail=100 <容器名>`。旧版按 [生产环境更新步骤](UPDATING.md) 升级后，在设置中启用开关。

详细日志包括：

- 每轮检查开始和结束、启用规则数量、监控账号数量、检查间隔、跳过/繁忙原因。
- 请求的 HTTP 方法、主站 Host、完整接口路径、安全查询参数、请求编号。
- 请求响应状态、耗时及成功/HTTP 错误/网络取消/响应格式异常等分类。
- 账号快照的用量和采样时间、建立基线/等待更新/归零复核等状态。
- Sub2API 自动更新的使用记录、检查更新、执行更新、重启和运行版本请求，以及版本检查、空闲等待和重启后核对阶段。

请求日志格式示例（时间、ID 与耗时为示例值）：

```text
INFO "sub2api 请求" request_id=1 method=GET host=sub2api:8080 path=/api/v1/admin/accounts/12 phase=start
INFO "sub2api 请求" request_id=1 method=GET host=sub2api:8080 path=/api/v1/admin/accounts/12 phase=end http_status=200 duration_ms=18 outcome=success
```

管理员 Key、Cookie、通知凭据、请求/响应正文不写入详细日志，自由文本搜索参数脱敏。开启日志不会增加接口请求，也不会触发任何账号上游查询。

关闭详细运行日志后，不输出自动更新的接口请求明细和阶段诊断；自动更新开始、确认成功及异常等关键结果仍写入常规日志。

未启用监控规则或没有选定来源账号时，额度监控不会请求主站；若另行启用了 Sub2API 自动更新，它仍会按设置检查使用记录和更新状态。查看周期日志中的数量和跳过原因。快照未更新时仍等待，不会因开启日志而补查上游。

## Telegram 手动重置

全局自动重置关闭时，启用规则并选择 Telegram 通知、目标订阅与日/周/月周期。检测到新的有效归零事件后，通知显示绑定的订阅和重置范围，并提供“重置选定订阅”“忽略”按钮；规则的自动重置开关可保持关闭。

- 点击重置只批准这一份通知绑定的目标，不会开启全局或规则自动开关。
- 点击忽略不修改订阅；重复点击、重复回调和服务重启不会重复清零。
- 私聊只允许配置的收件人操作。群组需要在 Telegram 设置中填写允许操作的用户 ID；未配置群权限时仍可收到普通通知，普通群成员不会获得重置权限。
- 请求默认有效期为 24 小时。站点、规则目标/周期、Bot、聊天或授权用户变更后，旧按钮失效；相关订阅出现更新的归零事件时，旧请求也会失效。
- 执行前再次核对有效订阅、用户及分组归属，结果会通过 Telegram 通知，并写入“事件历史”的手动请求与订阅执行记录。结果未知时仍停止重放，先在主站核对。

回调使用 Telegram `getUpdates` 长轮询，只连接你配置的 Telegram Bot，不需要公网地址，也不访问 OpenAI。建议使用专用 Bot；同一个 Bot 不能同时由其他程序消费 `getUpdates`，也不能同时启用 Webhook。本服务不会删除或覆盖已有 Webhook；发生冲突时在 Telegram 设置显示接收器错误，需改用专用 Bot 或由你调整原程序。

空密码字段保存时保留已有凭据；清除操作使用页面专门的清除选项。主站地址变更会停用已有规则和自动更新、清空采样基线并取消待处理动作，站点、账号和订阅 ID 应重新核对后启用。

## 重置及失败语义

- 首次快照为零只建立基线。持续为零不重复触发；重新观察到非零后，更新的归零快照可再次触发，包括同一周内的人工重置。
- 所有规则均停用某账号后，再次启用会重新建立基线。停用期间的变化不会补发为新重置事件。
- 同一轮多个来源同时归零时，共同订阅按目标合并重置周期后执行一次，各账号保留各自事件与通知渠道。
- 仅重置当前状态 active 且处于有效期内的所选订阅。
- 日用量清零后仍按主站时区每日零点刷新；周/月用量清零后从实际执行时刻重新起算 7/30 天。
- 订阅有效期、额度上限、余额和历史用量日志保持主站现有重置语义。窗口无法精确对齐上游真实重置时刻。
- 使用 `/api/v1/admin/subscriptions/bulk-action` 的 `reset_quota` 与固定 `Idempotency-Key`，每批最多 100 项，目标总数无额外业务限制。
- 主站批量接口允许部分成功。页面逐项显示结果，只重试明确失败的目标；成功项不重新执行。
- 创建重试任务后原动作标记为已重试，避免再次点击旧失败动作重复清零。
- 请求超时、响应损坏等结果未知时标记 `unknown`，停止盲重试，请在主站核对。主站幂等记录有 TTL，且可能未启用协调器，不能保证永久严格只执行一次。
- 通知失败只重试通知，不重新重置订阅。服务恢复后曾处于执行中的动作标记为未知，避免重新发送可能已成功的请求。
- 归零观测不能区分自然周期、人工重置券或上游修正。

从此前主动采样版本升级时，旧采样基线会重新建立；未执行的旧来源动作会跳过，避免升级后补执行历史归零事件。已经执行的历史记录保留。

## 本地构建

需要 Go 1.27+、Node.js 22+ 和 pnpm：

```sh
cd web
pnpm install --frozen-lockfile
pnpm build
cd ..
go build -buildvcs=false -o quota-watch .
QUOTA_WATCH_PASSWORD='替换为登录密码' ./quota-watch
```

前端构建产物嵌入 Go 二进制，发布时不需要 Node。前端开发可在服务运行时执行 `pnpm dev`，由 Vite 代理 `/api` 到本地服务。

环境变量：

| 名称 | 默认/说明 |
| --- | --- |
| `QUOTA_WATCH_LISTEN` | `127.0.0.1:8091` |
| `QUOTA_WATCH_DATA_DIR` | `./data` |
| `QUOTA_WATCH_USERNAME` | `admin` |
| `QUOTA_WATCH_PASSWORD` | 管理页登录密码，启动时必须提供 |
| `QUOTA_WATCH_MASTER_KEY` | 可选，32 字节密钥的 Base64；未设置时在数据目录生成 `master.key` |

Linux systemd 模板见 `quota-watch.service`。创建专用用户，将二进制放在 `/opt/quota-watch`，将环境变量写入仅该服务可读的 `/etc/quota-watch.env`，安装服务后启动。

## 数据备份与升级

停止服务后备份整个数据目录，包含 `quota-watch.db`、可能存在的 WAL 文件与 `master.key`。使用环境变量密钥时也必须另行备份该密钥。恢复时保持原密钥，不能通过新生成密钥恢复旧加密配置。

Docker 部署的源码更新、保留旧数据、备份、验收及回滚命令见 [生产环境更新步骤](UPDATING.md)。后续新功能仍使用同一套更新流程；仅重启容器不会更新程序。

升级后先测试主站连接和模拟规则。主站实际部署必须在账号详情中暴露已有 Codex 快照字段，并支持订阅 bulk-action API；接口缺失或字段不兼容时等待数据，不会将数据补成零或主动查询上游。
